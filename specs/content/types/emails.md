# Transactional Emails — Content Guidelines

Source: transactionalEmailPushNotifications.pdf (Bitso, March 2026)

---

## Purpose

Transactional emails must be **clear, concise, and user-friendly**, reflecting Bitso's tone and voice. They build trust and reduce support contacts.

A **transactional email** is triggered by a user's specific action (deposit, purchase, withdrawal). It confirms or provides essential information. The user expects it.

---

## Goals (NNG Framework)

Every transactional email must achieve all three:

1. **Avoid being mistaken for spam** — survive users' ruthless inbox pruning
2. **Be a customer service ambassador** — enhance confidence in Bitso
3. **Prevent support calls** — answer all common questions in plain language

---

## The FEEL Framework

Apply to every part of an email:

| Dimension | What it means |
|---|---|
| **F**unctional | Delivers the essential information clearly and accurately |
| **E**motional | Uses appropriate tone (warmth, reassurance, accountability) |
| **E**ducational | Sets correct expectations; teaches users what the process looks like |
| **L**earning | Reinforces habits and helps users act confidently in the future |

---

## Email Structure (Deposits & Withdrawals)

All transactional emails share the same anatomy: Subject → Title → Body → Details table → Footer.

### Subject line rules
- **Processing**: Neutral, factual — "Estamos procesando el depósito"
- **Success**: Celebratory with exclamation — "¡El depósito ya está disponible en tu cuenta!"
- **Failed**: Direct acknowledgement — "No pudimos procesar el depósito"

### Title rules
- Always open with the user's name: **"Hola, [Name]."**
- One sentence that confirms the event status

### Body rules
- Tell the user exactly what happens next (or what to do)
- Processing: "Te avisaremos cuando tengas el monto disponible en tu cuenta."
- Success: "Revisa los detalles a continuación:"
- Failed: "Por favor, inténtalo de nuevo. Si tienes dudas, contacta a nuestro equipo de soporte."

### Transaction details table (always include)
Required fields (add extras based on currency/transaction type):
- Monto
- Comisión
- Remitente
- Origen
- Estado
- Fecha y hora

The table is purely informative — no emotional language.

### Footer (standard — never alter)
> "En Bitso, nunca te pediremos información como contraseñas o credenciales por correo electrónico.
> Si tienes alguna duda, puedes contactarnos a través de nuestra app en la sección de Ayuda o visitar bitso.com.
> © 2014–2025 Bitso. Todos los derechos reservados"

Purpose: phishing warning + trust-building.

## State-by-State Copy Patterns

### Deposits

| State | Subject | Title | Body tone |
|---|---|---|---|
| Processing | "Estamos procesando el depósito" | "Hola, [Name]. El depósito se está procesando" | Neutral, factual; set expectation that Bitso will notify |
| Success | "¡El depósito ya está disponible en tu cuenta!" | "Hola, [Name]. El monto ya está disponible en tu cuenta" | Celebratory; use exclamation |
| Failed | "No pudimos procesar el depósito" | "Hola, [Name]. Tuvimos un problema técnico" | Direct + accountable; "tuvimos" softens, shows accountability |

### Withdrawals

| State | Subject | Title | Body tone |
|---|---|---|---|
| Processing | "Estamos procesando tu transferencia" | "Hola, [Name]. Tu transferencia se está procesando" | Neutral, factual |
| Success | "¡Tu transferencia se completó con éxito!" | "Hola, [Name]. Tu transferencia se envió a la cuenta de destino" | Celebratory; "con éxito" is the positive marker |
| Failed | "No pudimos procesar la transferencia" | "Hola, [Name]. Tuvimos un problema técnico" | Direct + accountable |

---

## Tone by State

| State | Emotional register | What NOT to do |
|---|---|---|
| Processing | Neutral, calm — no false promises | Don't add excitement or urgency |
| Success | Warm, celebratory — use `¡…!` in subject | Don't be robotic or overly formal |
| Failed | Accountable, supportive — use "tuvimos" (we had) not "hubo" (there was) | Don't blame the user; don't be alarming |

## FEEL Checklist for Transactional Emails

**Functional**
- [ ] Subject line clearly states the event outcome
- [ ] Title confirms event + includes user's name
- [ ] Body tells the user what happens next (or what to do)
- [ ] Details table is complete with all required fields
- [ ] Footer contains the standard phishing warning

**Emotional**
- [ ] User's name is used in the title
- [ ] Tone matches the state (neutral / celebratory / accountable)
- [ ] Failed state uses "tuvimos un problema" framing (shared accountability)
- [ ] No alarming or dismissive language

**Educational**
- [ ] Processing state sets the expectation correctly ("Bitso te avisará")
- [ ] Failed state tells the user what to do next
- [ ] Details table is consistent and predictable

**Learning**
- [ ] Failed state normalizes contacting support when needed
- [ ] Footer reinforces phishing awareness
- [ ] User can complete their task without contacting support
